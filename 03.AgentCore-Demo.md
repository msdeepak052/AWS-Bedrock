## What is a Strands Agent?

**Strands Agents** is an **open-source AWS agent framework** for building AI agents in Python.

Think of it as:

> **Strands = the code/framework that builds the "brain + orchestration" of your agent.**

It is **not the same thing as AgentCore**.

```text
Strands Agent
     │
     │ "What should I do?"
     ▼
   LLM
     │
     │ decides to use a tool
     ▼
   Tool
     │
     ▼
  Result
     │
     ▼
   LLM
     │
     ▼
 Final Answer
```

### Simple example

Suppose we create a **Kubernetes Investigation Agent**.

```python
from strands import Agent, tool


@tool
def get_pods():
    """Get Kubernetes pod status."""
    return """
    payment-service-abc   Running
    payment-service-xyz   CrashLoopBackOff
    """


agent = Agent(
    tools=[get_pods]
)

response = agent(
    "Why is payment-service failing?"
)

print(response)
```

The flow is:

```text
User
 │
 │ "Why is payment-service failing?"
 ▼
Strands Agent
 │
 ▼
LLM
 │
 │ decides:
 │ "I need Kubernetes pod information"
 ▼
get_pods()
 │
 ▼
Kubernetes result
 │
 ▼
LLM analyzes result
 │
 ▼
"payment-service-xyz is in
CrashLoopBackOff..."
```

### Strands vs AgentCore

This distinction is **very important**:

| Strands                     | AgentCore                 |
| --------------------------- | ------------------------- |
| Agent development framework | Production agent platform |
| Builds the agent logic      | Runs/operates the agent   |
| Provides agent loop         | Provides Runtime          |
| Defines tools               | Provides Gateway          |
| Uses LLMs                   | Provides Memory           |
| Python framework            | Provides Identity         |
|                             | Provides Observability    |

Think:

```text
             YOUR AI APPLICATION
                    │
                    ▼
             ┌─────────────┐
             │   STRANDS   │
             │    AGENT    │
             │             │
             │ Think       │
             │ Plan        │
             │ Use tools   │
             └──────┬──────┘
                    │
                    ▼
             ┌─────────────┐
             │  AGENTCORE  │
             │             │
             │ Runtime     │
             │ Gateway     │
             │ Memory      │
             │ Identity    │
             │ Observability│
             └─────────────┘
```

**Interview one-liner:**

> **"Strands Agents is an AWS open-source framework for building model-driven agents with tools and workflows, while AgentCore provides the managed infrastructure to deploy and operate those agents securely at scale."**

* **Gateway** — exposes K8s operations as MCP tools

The current AgentCore documentation confirms that Runtime supports HTTP/MCP/A2A, Gateway can expose Lambda functions as MCP-compatible tools, Memory can be created from the console, and AgentCore provides CloudWatch/OTEL observability. ([AWS Documentation][1])

# 1. What are we building?

Our final system will answer questions such as:

> "Why is `payment-service` failing in production?"

The agent will automatically investigate:

```text
1. Get pods
2. Find unhealthy pod
3. Get pod status
4. Get pod logs
5. Get Kubernetes events
6. Get deployment configuration
7. Analyze everything with Claude
8. Give root-cause hypothesis
9. Recommend remediation
```

Importantly, this first version will be **READ-ONLY**.

It will **not**:

```text
kubectl delete
kubectl rollout restart
kubectl scale
kubectl patch
```

That's deliberate for a production-style first implementation.

# 10. Lambda code

Create:

`lambda/lambda_function.py`

```python
import json
import os
import base64
import tempfile

import boto3

from kubernetes import client


EKS_CLUSTER_NAME = os.environ["EKS_CLUSTER_NAME"]
AWS_REGION = os.environ["AWS_REGION_NAME"]
DEFAULT_NAMESPACE = os.environ.get(
    "DEFAULT_NAMESPACE",
    "production"
)


def get_eks_client():
    """
    Build a Kubernetes API client using the EKS cluster
    endpoint and CA certificate.
    """

    eks = boto3.client(
        "eks",
        region_name=AWS_REGION
    )

    cluster = eks.describe_cluster(
        name=EKS_CLUSTER_NAME
    )["cluster"]

    endpoint = cluster["endpoint"]

    ca_data = cluster["certificateAuthority"]["data"]

    with tempfile.NamedTemporaryFile(
        delete=False
    ) as ca_file:

        ca_file.write(
            base64.b64decode(ca_data)
        )

        ca_path = ca_file.name

    # Generate an EKS authentication token
    token = generate_eks_token()

    configuration = client.Configuration()

    configuration.host = endpoint

    configuration.ssl_ca_cert = ca_path

    configuration.api_key = {
        "authorization": f"Bearer {token}"
    }

    configuration.verify_ssl = True

    api_client = client.ApiClient(
        configuration=configuration
    )

    return api_client


def generate_eks_token():

    sts = boto3.client(
        "sts",
        region_name=AWS_REGION
    )

    # Simplified token generation approach.
    # For production, use the supported EKS token
    # generation implementation/library.

    import subprocess

    result = subprocess.check_output(
        [
            "aws",
            "eks",
            "get-token",
            "--cluster-name",
            EKS_CLUSTER_NAME,
            "--region",
            AWS_REGION,
        ]
    )

    response = json.loads(result)

    return response["status"]["token"]


def get_pods(namespace):

    api_client = get_eks_client()

    v1 = client.CoreV1Api(
        api_client
    )

    pods = v1.list_namespaced_pod(
        namespace=namespace
    )

    results = []

    for pod in pods.items:

        results.append(
            {
                "name": pod.metadata.name,
                "phase": pod.status.phase,
                "node": pod.spec.node_name,
                "pod_ip": pod.status.pod_ip,
                "container_statuses": [
                    {
                        "name": status.name,
                        "ready": status.ready,
                        "restart_count": status.restart_count,
                        "reason": (
                            status.state.waiting.reason
                            if status.state.waiting
                            else None
                        ),
                    }
                    for status in (
                        pod.status.container_statuses or []
                    )
                ],
            }
        )

    return results


def get_pod_logs(
    namespace,
    pod_name,
    container=None,
    tail_lines=100
):

    api_client = get_eks_client()

    v1 = client.CoreV1Api(
        api_client
    )

    logs = v1.read_namespaced_pod_log(
        name=pod_name,
        namespace=namespace,
        container=container,
        tail_lines=tail_lines
    )

    return {
        "pod": pod_name,
        "namespace": namespace,
        "logs": logs
    }


def get_events(namespace):

    api_client = get_eks_client()

    v1 = client.CoreV1Api(
        api_client
    )

    events = v1.list_namespaced_event(
        namespace=namespace
    )

    results = []

    for event in events.items:

        results.append(
            {
                "reason": event.reason,
                "message": event.message,
                "type": event.type,
                "object": (
                    event.involved_object.name
                ),
                "last_timestamp": (
                    str(event.last_timestamp)
                ),
            }
        )

    return results


def get_deployment(
    namespace,
    deployment_name
):

    api_client = get_eks_client()

    apps = client.AppsV1Api(
        api_client
    )

    deployment = apps.read_namespaced_deployment(
        name=deployment_name,
        namespace=namespace
    )

    containers = []

    for container in (
        deployment.spec.template.spec.containers
    ):

        containers.append(
            {
                "name": container.name,
                "image": container.image,
                "resources": {
                    "requests": (
                        container.resources.requests
                        if container.resources
                        else None
                    ),
                    "limits": (
                        container.resources.limits
                        if container.resources
                        else None
                    ),
                },
            }
        )

    return {
        "name": deployment.metadata.name,
        "namespace": namespace,
        "replicas": deployment.spec.replicas,
        "available_replicas": (
            deployment.status.available_replicas
        ),
        "containers": containers,
    }


def lambda_handler(event, context):

    print(
        "Received event:",
        json.dumps(event)
    )

    tool_name = event.get(
        "tool_name"
    )

    arguments = event.get(
        "arguments",
        {}
    )

    namespace = arguments.get(
        "namespace",
        DEFAULT_NAMESPACE
    )

    if tool_name == "get_pods":

        result = get_pods(
            namespace
        )

    elif tool_name == "get_pod_logs":

        result = get_pod_logs(
            namespace=namespace,
            pod_name=arguments["pod_name"],
            container=arguments.get("container"),
            tail_lines=arguments.get(
                "tail_lines",
                100
            )
        )

    elif tool_name == "get_events":

        result = get_events(
            namespace
        )

    elif tool_name == "get_deployment":

        result = get_deployment(
            namespace=namespace,
            deployment_name=arguments[
                "deployment_name"
            ]
        )

    else:

        raise ValueError(
            f"Unknown tool: {tool_name}"
        )

    return {
        "statusCode": 200,
        "body": result
    }
```

### Important correction for a real Lambda deployment

The above uses the AWS CLI to generate the EKS token, which means you'd also need the AWS CLI packaged in Lambda. **For the actual production deployment, don't use this approach.**

We'll use the Python `boto3`/EKS token generation approach or a dedicated EKS auth library instead.

For a production implementation, I would package the EKS authentication cleanly rather than shipping the CLI into Lambda.

# 17. Create a read-only Kubernetes role

Create:

`k8s-readonly.yaml`

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: ai-investigation-readonly
rules:

  - apiGroups: [""]
    resources:
      - pods
      - pods/log
      - events
      - services
    verbs:
      - get
      - list

  - apiGroups: ["apps"]
    resources:
      - deployments
      - replicasets
    verbs:
      - get
      - list
```

Apply:

```bash
kubectl apply -f k8s-readonly.yaml
```

Then map your Lambda IAM identity into Kubernetes using the EKS access-entry mechanism appropriate to your cluster.

Conceptually:

```text
Lambda IAM Role
       │
       ▼
EKS Access Entry
       │
       ▼
Kubernetes RBAC
       │
       ▼
ClusterRole:
ai-investigation-readonly
```

This means even if the AI tries:

```text
delete pod
```

Kubernetes should reject it.

That's **defense in depth**.

# 26. Agent code

`agent/agent.py`

```python
import os

from strands import Agent
from strands.models import BedrockModel

from bedrock_agentcore.runtime import BedrockAgentCoreApp


app = BedrockAgentCoreApp()


SYSTEM_PROMPT = """
You are a Kubernetes Site Reliability Engineering investigation agent.

Your job is to investigate Kubernetes incidents.

You are READ ONLY.

You MUST NOT:
- delete pods
- restart deployments
- scale workloads
- patch resources
- modify Kubernetes resources

You MAY:
- inspect pods
- inspect pod logs
- inspect Kubernetes events
- inspect deployment configuration

Investigation methodology:

1. Identify the affected service.
2. Inspect pods.
3. Identify unhealthy pods.
4. Inspect pod logs.
5. Inspect Kubernetes events.
6. Inspect deployment configuration.
7. Correlate evidence.
8. Determine the most likely root cause.
9. Provide supporting evidence.
10. Provide recommended remediation.

Never claim certainty when evidence is insufficient.

Always clearly separate:
- Observed facts
- Root cause hypothesis
- Recommended action

If the user does not provide a namespace, use "production".
"""


model = BedrockModel(
    model_id=os.environ.get(
        "MODEL_ID",
        "anthropic.claude-3-5-sonnet-20241022-v2:0"
    ),
    region_name=os.environ.get(
        "AWS_REGION",
        "ap-south-1"
    )
)


agent = Agent(
    model=model,
    system_prompt=SYSTEM_PROMPT
)


@app.entrypoint
def invoke(payload):

    user_message = payload.get(
        "prompt",
        ""
    )

    if not user_message:

        return {
            "error": "prompt is required"
        }

    response = agent(
        user_message
    )

    return {
        "response": str(response)
    }


if __name__ == "__main__":
    app.run()
```

def create_mcp_client():

# 45. What is actually "Agentic" here?

This is important.

If we wrote:

```python
get_pods()
get_logs()
get_events()
```

ourselves in a fixed sequence, that's just an application workflow.

An agent becomes more interesting when the LLM decides:

```text
Question
   ↓
Reason
   ↓
Which tool?
   ↓
Tool
   ↓
Result
   ↓
Reason again
   ↓
Which next tool?
```

For example:

### Incident A

```text
Question
 ↓
get_pods
 ↓
OOMKilled
 ↓
get_deployment
 ↓
memory limit
 ↓
Answer
```

### Incident B

```text
Question
 ↓
get_pods
 ↓
Pending
 ↓
get_events
 ↓
Insufficient CPU
 ↓
get_deployment
 ↓
Answer
```

### Incident C

```text
Question
 ↓
get_pods
 ↓
Running
 ↓
get_logs
 ↓
DB timeout
 ↓
Answer
```

The **tool sequence changes based on evidence**.

That's agentic behavior.

## One correction to the earlier explanation

One subtle but important point for your notes: **AgentCore Gateway is not merely an "MCP gateway."** The current AWS documentation describes it more broadly as a managed AI gateway that can connect agents to tools, other agents and model providers; MCP is one of its major interfaces. ([AWS Documentation][12])

Also, AgentCore Runtime can be used directly for MCP servers, so **Gateway and Runtime are complementary rather than interchangeable**. AWS documents Runtime as supporting HTTP, MCP and A2A protocols. ([AWS Documentation][13])

For the actual lab, I'd build **Phase 1 first with a deliberately simple read-only EKS setup**, verify the agent, then put **Gateway + MCP + Memory + Identity + Observability** around it. That gives you a much better understanding than trying to create all six services simultaneously.

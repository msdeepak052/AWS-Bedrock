> **“AWS gives you one managed platform/API where you can use different AI foundation models without building and managing the AI infrastructure yourself.”**

AWS describes Bedrock as a fully managed service providing access to foundation models from multiple providers through AWS. ([AWS Documentation][1])

# 2. What exactly is Bedrock?

Think of Bedrock as an **AI gateway/platform**.

```text
                 AMAZON BEDROCK
                       │
        ┌──────────────┼──────────────┐
        │              │              │
        ▼              ▼              ▼
   Foundation      Knowledge       Agents /
     Models          Bases         AgentCore
        │              │              │
        ▼              ▼              ▼
   Generate AI       RAG          Take actions
   responses       with data
```

Bedrock provides capabilities around foundation models, RAG/Knowledge Bases, agents, model customization, evaluation, and other generative-AI functionality. ([AWS Documentation][2])

# 9. What is an embedding?

This is important for understanding RAG.

Suppose we have:

```text
"Kubernetes Pod runs containers"
```

An embedding model converts that text into numbers:

```text
"Kubernetes Pod runs containers"

             ↓

[0.12, -0.44, 0.81, 0.22, ...]
```

That numerical representation is called a **vector embedding**.

Now:

```text
"K8s pod executes containers"
```

will produce a vector that is mathematically close to the first one.

So the system understands that:

```text
"Kubernetes Pod runs containers"

        ≈

"K8s pod executes containers"
```

even though the exact words differ.

# 10. RAG workflow — very important

Suppose user asks:

> **"What is our company's minimum number of replicas?"**

The workflow becomes:

```text
USER
 │
 │ "minimum replicas?"
 ▼
BEDROCK KNOWLEDGE BASE
 │
 ▼
Convert question → embedding
 │
 ▼
Search vector database
 │
 ▼
Find relevant document chunk
 │
 │
 │ "Production requires
 │  minimum 3 replicas"
 ▼
Add retrieved information
to prompt
 │
 ▼
FOUNDATION MODEL
 │
 ▼
Generate answer
 │
 ▼
USER
```

This is the core Bedrock RAG architecture.

AWS describes the runtime process as converting the query into a vector, searching the vector index for semantically similar chunks, augmenting the prompt with those chunks, and sending the resulting prompt to the model. ([AWS Documentation][4])

# 12. Now understand Bedrock Agent

Suppose you don't just want the AI to **answer**.

You want it to **perform an action**.

User:

> "Check why my production pod is crashing."

An AI agent could potentially:

```text
User
 │
 ▼
Bedrock Agent / AgentCore
 │
 ├── Understand request
 │
 ├── Query knowledge base
 │
 ├── Call an API/tool
 │
 ├── Retrieve Kubernetes information
 │
 ├── Analyze result
 │
 └── Generate response
 │
 ▼
User
```

Agents are designed to orchestrate interactions between the foundation model, data sources, applications, and conversations, including calling APIs and using knowledge bases. ([AWS Documentation][5])

**Important current AWS terminology:** Bedrock Agents launched in 2023 are now called **Amazon Bedrock Agents Classic**, and AWS says new customers have been directed toward **Amazon Bedrock AgentCore** since July 30, 2026. Existing Agents Classic customers can continue using it. ([AWS Documentation][6])

# 1. What is Amazon Bedrock Knowledge Base?

A **Bedrock Knowledge Base (KB)** lets an LLM answer questions using your **private/company data** rather than relying only on what the foundation model learned during training.

AWS describes Knowledge Bases as a managed way to implement RAG: ingest data, create embeddings/index it, retrieve relevant content, and use that content to improve generated answers. ([AWS Documentation][1])

For example, suppose your company has:

```text
S3
├── DevOps_Runbook.pdf
├── EKS_Troubleshooting.pdf
├── Security_Policies.pdf
├── Deployment_Guide.pdf
└── Incident_Reports.pdf
```

Your LLM doesn't automatically know those documents.

Knowledge Base allows:

```text
Company Documents
       ↓
Bedrock Knowledge Base
       ↓
RAG retrieval
       ↓
Relevant information
       ↓
LLM
       ↓
Answer
```

Each chunk gets represented as an embedding.

# 7. What is an embedding?

An embedding converts text into a numerical vector representing its semantic meaning.

For example, conceptually:

```text
"EKS pod OOMKilled"
        ↓
[0.21, -0.14, 0.82, 0.33, ...]
```

And:

```text
"Container exceeded memory limit"
        ↓
[0.19, -0.12, 0.79, 0.31, ...]
```

Because their meanings are similar, their vectors can be close in vector space.

That's what allows semantic search.

# 13. What exactly does the Agent call?

There are two common approaches you should distinguish.

## Approach A — Direct Knowledge Base API

Your application can directly query a Knowledge Base using APIs such as:

```text

RetrieveAndGenerate
```

AWS documents `Retrieve` as returning relevant source chunks, while `RetrieveAndGenerate` combines retrieval with model generation. ([AWS Documentation][3])

Conceptually:

```python
response = bedrock_agent_runtime.retrieve(
    knowledgeBaseId="KB123456",
    retrievalQuery={
        "text": "What is our EKS OOMKilled procedure?"
    }
)
```

Then your application takes the returned chunks and passes them to the LLM.

# 14. `RetrieveAndGenerate`

AWS also provides:

```text
RetrieveAndGenerate
```

which combines retrieval and generation.

Conceptually:

```python
response = bedrock_agent_runtime.retrieve_and_generate(
    input={
        "text": "What is our EKS OOMKilled procedure?"
    },
    retrieveAndGenerateConfiguration={
        "knowledgeBaseConfiguration": {
            "knowledgeBaseId": "KB123456",
            "modelArn": "..."
        },
        "type": "KNOWLEDGE_BASE"
    }
)
```

The service performs the retrieval and generation and can return citations. ([AWS Documentation][4])

**Important current AWS nuance:** AWS's current documentation says `RetrieveAndGenerate` cannot be used with **Managed Knowledge Bases**; for those, use `Retrieve` or agentic retrieval such as `AgenticRetrieveStream`. ([AWS Documentation][4])

# 18. Knowledge Base vs S3

A common interview question:

> "Why not just give the LLM an S3 bucket?"

Because S3 is primarily object storage:

```text
S3
 ↓
stores PDFs/docs
```

Knowledge Base adds the RAG machinery:

```text
S3
 ↓
ingestion
 ↓
chunking
 ↓
embeddings
 ↓
vector index
 ↓
retrieval
 ↓
LLM context
```

So:

```text
S3 = storage

Knowledge Base = RAG/retrieval layer over your knowledge
```

# 19. Knowledge Base vs fine-tuning

This is **very important**.

Suppose you have:

```text
Company DevOps documentation
```

You usually don't fine-tune the model just to make it know those documents.

### Fine-tuning

Changes model behavior/weights for a particular task/style.

### RAG

Provides relevant external information at inference time.

```text
RAG:

Document
 ↓
Knowledge Base
 ↓
Retrieve
 ↓
Prompt/context
 ↓
LLM
```

For frequently changing company documentation, RAG is generally much more appropriate because you can update/re-sync the knowledge source rather than retraining the model.

# 21. One important current AWS distinction

AWS now distinguishes between **Managed Knowledge Bases** and **Customer-managed Knowledge Bases**.

Managed:

```text
AWS manages much of:

ingestion
indexing
storage/retrieval infrastructure
```

Customer-managed:

```text
You manage more of:

vector store
ingestion
parsing
indexing
configuration
```

AWS currently recommends Managed Knowledge Base for an optimized managed experience. ([AWS Documentation][1])

Also, AWS's current documentation says **Bedrock Agents Classic** is in maintenance mode for existing customers and is no longer open to new customers starting July 30, 2026; AWS points new agentic workloads toward **Amazon Bedrock AgentCore**. ([AWS Documentation][2])

So if you're preparing for a **2026 interview**, I'd say:

> "Historically, Bedrock Agents could directly associate a Knowledge Base. For new AWS architectures, I would also evaluate Bedrock AgentCore and the current Managed Knowledge Base capabilities."
